
## Настройка с виртуальным UEFI
Для тестирования скриптов установки Arch Linux на QEMU можно создать виртуальную машину с GPT-разметкой, использовать LVM, а также загрузиться через виртуальное UEFI, чтобы симулировать реальные условия, которые вам нужны для отладки. Вот как это можно сделать.

### 1. Создание виртуального диска с GPT и LVM

Сначала создайте виртуальный диск для вашей машины:

```bash
qemu-img create -f qcow2 archlinux_vm_disk.qcow2 20G
```

Этот диск будет использоваться в качестве основного жёсткого диска. Формат `qcow2` удобен, так как поддерживает динамическое увеличение размера.

### 2. Подготовка конфигурации для запуска QEMU с UEFI и ISO-образом Arch Linux

Чтобы запустить виртуальную машину в QEMU с UEFI и подключить ISO-образ, потребуется установить `OVMF`, обеспечивающий поддержку виртуального UEFI. В Arch Linux пакет OVMF можно установить следующим образом:

```bash
sudo pacman -S edk2-ovmf
```

После установки, найдите расположение UEFI-файлов (`OVMF_CODE.fd` и `OVMF_VARS.fd`), обычно они находятся в директории `/usr/share/edk2-ovmf/`. Вам понадобится `OVMF_CODE.fd` для конфигурации QEMU.

Теперь создайте команду для запуска виртуальной машины с поддержкой UEFI:

```bash
qemu-system-x86_64 \
    -enable-kvm \
    -m 2G \
    -cpu host \
    -smp 2 \
    -drive if=pflash,format=raw,readonly=on,file=/usr/share/edk2-ovmf/OVMF_CODE.fd \
    -drive if=pflash,format=raw,file=/path/to/OVMF_VARS.fd \
    -drive file=archlinux_vm_disk.qcow2,format=qcow2 \
    -cdrom /path/to/archlinux.iso \
    -boot order=d \
    -nic user,model=virtio-net-pci \
    -vga virtio
```

#### Пояснения к опциям:
- `-enable-kvm` — включает поддержку аппаратной виртуализации (если доступна).
- `-m 2G` — выделяет 2 ГБ ОЗУ.
- `-cpu host` — использует тип CPU хоста для большей производительности.
- `-smp 2` — устанавливает 2 виртуальных процессора.
- `-drive if=pflash...` — подключает UEFI BIOS (OVMF).
- `-drive file=archlinux_vm_disk.qcow2,format=qcow2` — подключает основной виртуальный диск.
- `-cdrom /path/to/archlinux.iso` — путь к ISO-образу Arch Linux для загрузки установщика.
- `-boot order=d` — указывает загрузку с CD (ISO-образа).
- `-nic user,model=virtio-net-pci` — подключает виртуальный сетевой интерфейс с драйвером Virtio.
- `-vga virtio` — включает поддержку Virtio графики для лучшей производительности.

### 3. Использование GPT и LVM в установке

Загрузившись в установочный образ Arch Linux, можно вручную настроить GPT-разметку и LVM:

1. **Создайте GPT-разметку**:

    ```bash
    parted /dev/vda mklabel gpt
    ```

2. **Создайте разделы**:
    - EFI-раздел (например, 300 МБ, тип: `EFI System`).
    - Раздел для LVM.

    ```bash
    parted /dev/vda mkpart ESP fat32 1MiB 301MiB
    parted /dev/vda set 1 boot on
    parted /dev/vda mkpart primary 301MiB 100%
    ```

3. **Настройка LVM**:
    - Инициализируйте физический том:

        ```bash
        pvcreate /dev/vda2
        ```

    - Создайте volume group (например, `vg0`):

        ```bash
        vgcreate vg0 /dev/vda2
        ```

    - Создайте логические тома (например, для корневой системы и swap):

        ```bash
        lvcreate -L 15G vg0 -n root
        lvcreate -L 2G vg0 -n swap
        ```

4. **Форматирование разделов**:
    - EFI-раздел:

        ```bash
        mkfs.fat -F32 /dev/vda1
        ```

    - LVM-разделы:

        ```bash
        mkfs.ext4 /dev/vg0/root
        mkswap /dev/vg0/swap
        ```

5. **Монтирование**:

    ```bash
    mount /dev/vg0/root /mnt
    mkdir -p /mnt/boot
    mount /dev/vda1 /mnt/boot
    swapon /dev/vg0/swap
    ```

Теперь можно приступать к установке Arch Linux, следуя обычной инструкции по установке, и запускать свои скрипты для проверки их работы.

### 4. Тестирование EFI и загрузчика

После завершения установки и установки загрузчика (например, `systemd-boot` или `GRUB` с поддержкой EFI), перезагрузите виртуальную машину, отключив ISO-диск:

```bash
qemu-system-x86_64 \
    -enable-kvm \
    -m 2G \
    -cpu host \
    -smp 2 \
    -drive if=pflash,format=raw,readonly=on,file=/usr/share/edk2-ovmf/OVMF_CODE.fd \
    -drive if=pflash,format=raw,file=/path/to/OVMF_VARS.fd \
    -drive file=archlinux_vm_disk.qcow2,format=qcow2 \
    -nic user,model=virtio-net-pci \
    -vga virtio
```

Теперь машина загрузится с установленной системы на виртуальном диске, и вы сможете проверить, как работают ваши скрипты в условиях, приближенных к реальному железу.


## Рецепты по кешированию пакетов

Да, можно настроить кэширование пакетов для установки Arch Linux, чтобы каждый раз не скачивать их из интернета. Вот несколько подходов для создания локального кэша пакетов:

### 1. Использование `pacman`-кэша на локальном компьютере

Если у вас уже есть загруженные пакеты в кэше `pacman` на основном компьютере, можно поделиться ими с виртуальной машиной. Пакеты по умолчанию хранятся в директории `/var/cache/pacman/pkg`. Для этого:

1. **Создайте общую директорию для пакетов**:
   - Создайте временную папку, например, `~/archlinux-pkg-cache`.
   - Скопируйте туда все текущие пакеты из кэша `pacman`:

     ```bash
     mkdir -p ~/archlinux-pkg-cache
     cp -r /var/cache/pacman/pkg/* ~/archlinux-pkg-cache
     ```

2. **Подключите папку с пакетами к QEMU в режиме `virtio`**:
   - Используйте опцию `-virtfs` для подключения папки в качестве общего ресурса:

     ```bash
     qemu-system-x86_64 \
         -enable-kvm \
         -m 2G \
         -cpu host \
         -smp 2 \
         -drive file=archlinux_vm_disk.qcow2,format=qcow2 \
         -virtfs local,path=~/archlinux-pkg-cache,mount_tag=pkgcache,security_model=none \
         -nic user,model=virtio-net-pci \
         -vga virtio
     ```

3. **Подмонтируйте кэш на виртуальной машине**:
   - В виртуальной машине можно смонтировать общую папку с помощью `mount`:

     ```bash
     mkdir /mnt/pkgcache
     mount -t 9p -o trans=virtio pkgcache /mnt/pkgcache
     ```

4. **Настройте `pacman` для использования локального кэша**:
   - Создайте симлинк из кэша в систему:

     ```bash
     ln -s /mnt/pkgcache /var/cache/pacman/pkg
     ```

Теперь `pacman` будет использовать пакеты из вашего локального кэша и не будет повторно загружать их, если они уже там есть.

### 2. Создание локального зеркала с помощью `nginx` или `python -m http.server`

Если у вас много пакетов, можно создать локальный HTTP-сервер для раздачи пакетов:

1. **Настройте локальный HTTP-сервер**:
   - В каталоге с пакетами запустите HTTP-сервер на Python (например, на порту 8080):

     ```bash
     cd ~/archlinux-pkg-cache
     python3 -m http.server 8080
     ```

2. **Добавьте локальный репозиторий в `pacman.conf`**:
   - В виртуальной машине отредактируйте `/etc/pacman.conf` и добавьте локальное зеркало:

     ```ini
     [localrepo]
     SigLevel = Optional TrustAll
     Server = http://10.0.2.2:8080
     ```

     *(Замените `10.0.2.2` на IP-адрес хоста, если он отличается)*.

### 3. Использование `pacman` в режиме кэширующего прокси с `cower` или `pacserve`

Для более гибкого решения можно настроить `pacserve` — локальный кэширующий прокси-сервер для `pacman`, который автоматически раздаёт пакеты, имеющиеся на вашем компьютере.

1. **Установите `pacserve`**:

   ```bash
   sudo pacman -S pacserve
   ```

2. **Запустите `pacserve` на хосте**:

   ```bash
   sudo systemctl start pacserve
   ```

3. **Настройте виртуальную машину для использования `pacserve`**:
   - Отредактируйте `/etc/pacman.d/mirrorlist` на виртуальной машине, добавив ваш хост как зеркало:

     ```ini
     Server = http://10.0.2.2:15678/$repo/os/$arch
     ```

Теперь виртуальная машина будет сначала проверять локальный кэш `pacserve`, прежде чем пытаться загрузить пакеты из интернета.

### 4. Создание собственного локального репозитория

Если вам нужно протестировать конкретные версии пакетов или минимизировать доступ к внешним серверам, вы можете создать локальный репозиторий.

1. **Соберите нужные пакеты в одной папке**, например `~/myrepo`.
2. **Создайте индекс репозитория**:

   ```bash
   repo-add ~/myrepo/custom.db.tar.gz ~/myrepo/*.pkg.tar.zst
   ```

3. **Подключите этот репозиторий**:
   - Добавьте его в `/etc/pacman.conf`:

     ```ini
     [custom]
     SigLevel = Optional TrustAll
     Server = file:///home/user/myrepo
     ```

4. Теперь `pacman` будет использовать ваш локальный репозиторий.

### Заключение

Эти методы помогут вам экономить трафик и ускорить тестирование, используя кэширование пакетов локально. Выбор подхода зависит от частоты тестирования и объёма пакетов, необходимых для установки.

## Решение проблем с DNS

Это хороший вопрос! Если на физическом (реальном) оборудовании с тем же установочным ISO Arch Linux DNS работает корректно, а в виртуальной машине — нет, то это может быть связано с особенностями сети в виртуальной среде QEMU. Давайте разберёмся в возможных причинах.

### 1. **Особенности сети QEMU в режиме `user` (NAT)**

По умолчанию QEMU использует **user-mode сеть** (с опцией `-nic user`), которая работает через виртуальный NAT и предоставляет виртуальной машине доступ к сети хоста. Однако:

   - **User-mode сеть** не передаёт все сетевые пакеты и ограничена в поддержке некоторых протоколов, включая иногда нестабильную поддержку DNS.
   - QEMU в режиме NAT иногда использует встроенный DNS-сервер, что может привести к проблемам при попытке разрешения имён через `systemd-resolved`, особенно если настройки сети виртуальной машины и хоста конфликтуют.

### 2. **`systemd-resolved` и локальный DNS в QEMU**

В QEMU DNS-запросы из виртуальной машины отправляются на адрес **10.0.2.3** (внутренний DNS-сервер QEMU для user-mode сети). Это может конфликтовать с настройками `systemd-resolved`, который использует локальный адрес **127.0.0.53** как DNS-резолвер. 

На физическом оборудовании же система напрямую использует DNS-серверы, предоставленные маршрутизатором или DHCP-сервером, поэтому `systemd-resolved` работает корректно.

### 3. **Различия в DHCP-конфигурации**

Виртуальная машина получает свои сетевые настройки через **виртуальный DHCP-сервер QEMU**, а не через ваш маршрутизатор или DHCP-сервер вашей сети. QEMU автоматически настраивает IP-адрес и DNS-сервер (обычно 10.0.2.3), но эти настройки могут конфликтовать с `systemd-resolved`, который ожидает работы через 127.0.0.53.

На физическом оборудовании Arch Linux получает настройки DNS от вашего маршрутизатора, что делает процесс более прямым и надёжным.

### Как исправить проблему

Чтобы обойти проблемы с DNS в QEMU и `systemd-resolved`, есть несколько подходов:

#### Подход 1: Задать статические DNS-серверы

1. Отключите `systemd-resolved` и используйте статические настройки DNS, добавив DNS-серверы напрямую в `/etc/resolv.conf`:

   ```bash
   sudo systemctl stop systemd-resolved
   sudo systemctl disable systemd-resolved
   sudo rm /etc/resolv.conf
   echo -e "nameserver 8.8.8.8\nnameserver 1.1.1.1" | sudo tee /etc/resolv.conf
   ```

2. После этого DNS-запросы будут идти напрямую через указанные DNS-серверы (например, Google DNS и Cloudflare DNS).

#### Подход 2: Использовать `tap` и bridge-сеть

Если доступен bridge-сетевой интерфейс, настройте QEMU на использование **bridge-сети** вместо **user-mode**. Это позволит вашей виртуальной машине использовать DNS так же, как это делает физическая машина, поскольку она будет находиться в той же сети, что и хост.

```bash
sudo qemu-system-x86_64 \
    -enable-kvm \
    -m 2G \
    -cpu host \
    -nic tap,ifname=tap0,script=no,downscript=no,model=virtio-net-pci \
    ...
```

*(Потребуется настройка bridge на хосте и `tap0` интерфейса.)*

### Заключение

На физическом оборудовании DNS работает корректно, поскольку система получает DNS-серверы от маршрутизатора или сети напрямую. В виртуальной машине через QEMU DNS может не работать из-за ограничений `user-mode` сети и взаимодействия с `systemd-resolved`. Настройка статического DNS или использование `tap` интерфейса с bridge-сетью решает эту проблему.

Судя по результатам, ваш виртуальный адаптер в QEMU (`ens3`) настроен, и вы можете пинговать внешний IP-адрес (`8.8.8.8`), но пинги нестабильны, и доступ к доменным именам, например `google.com`, не работает. Это может быть связано с проблемами в разрешении DNS или с нестабильностью NAT-подключения в `user-mode` сети QEMU.

### Возможные причины и их решения

#### 1. Проблемы с DNS

Если вы можете пинговать IP-адреса, но не доменные имена, это скорее всего связано с тем, что виртуальная машина не может разрешить DNS-запросы. Это распространённая проблема в `user-mode` сети QEMU.

Попробуйте вручную настроить DNS-сервер, добавив Google DNS в `/etc/resolv.conf`:

```bash
echo "nameserver 8.8.8.8" > /etc/resolv.conf
```

После этого попробуйте снова пинговать доменные имена:

```bash
ping google.com
```

#### 2. Нестабильное соединение через `user-mode` сеть

Иногда `user-mode` сеть в QEMU работает нестабильно, что может привести к высоким значениям задержек и потере пакетов. Это ограничение `user-mode` сети, так как она реализует NAT, что не всегда обеспечивает стабильное подключение. В таких случаях можно попробовать следующие подходы:

- **Переключитесь на `tap`-сетевой интерфейс с использованием bridge-сети**. Это создаст более стабильное и производительное подключение для виртуальной машины, но требует дополнительной настройки на хосте. Пример настроек приведён ниже.

#### 3. Настройка сети через `tap` и bridge-сеть (более стабильное решение)

1. **Создайте bridge-интерфейс** на хосте (если он ещё не настроен):

   ```bash
   sudo ip link add name br0 type bridge
   sudo ip link set dev br0 up
   ```

2. **Подключите `tap` интерфейс к bridge**. Добавьте `tap` интерфейс при запуске QEMU:

   ```bash
   sudo ip tuntap add dev tap0 mode tap
   sudo ip link set tap0 up
   sudo ip link set tap0 master br0
   ```

3. **Запустите QEMU с `tap` интерфейсом**:

   ```bash
   sudo qemu-system-x86_64 \
       -enable-kvm \
       -m 2G \
       -cpu host \
       -smp 2 \
       -drive if=pflash,format=raw,readonly=on,file=/usr/share/edk2-ovmf/x64/OVMF_CODE.fd \
       -drive if=pflash,format=raw,file=/usr/share/edk2-ovmf/x64/OVMF_VARS.fd \
       -drive file=/home/mega/data/extra/vm_disks/archlinux_vm_disk.qcow2,format=qcow2 \
       -virtfs local,path=/home/mega/git/Pure-Arch-Linux_-installer-v2/,mount_tag=inst_scripts,security_model=none \
       -cdrom /home/mega/data/extra/torrents/archlinux-2024.11.01-x86_64.iso \
       -drive file=../mntfld.iso,media=cdrom \
       -boot order=d \
       -netdev tap,id=mynet0,ifname=tap0,script=no,downscript=no \
       -device virtio-net-pci,netdev=mynet0 \
       -vga virtio
   ```

   Этот метод использует bridge-сеть на хосте, предоставляя виртуальной машине более надёжное соединение, как если бы она находилась в той же сети, что и хост. Убедитесь, что ваш хост правильно настроен для работы с bridge-сетью.

#### 4. Проверка фаервола

Также убедитесь, что фаервол на хосте не блокирует трафик для QEMU. Это может повлиять на стабильность соединения.

### Заключение

Если вам требуется стабильное и надёжное подключение, `tap`-интерфейс с bridge-сетью является лучшим вариантом. `user-mode` сеть удобна для быстрой настройки, но может быть нестабильной и плохо подходит для серьёзной работы с сетью.
